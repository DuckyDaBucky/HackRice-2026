# Account profiles and invitation roadmap

## Current account profile foundation

`/api/profile` requires Clerk authentication in every environment. GET returns only the authenticated user's profile; PUT accepts a confirmed structured profile and expected version, reclassifies experience with Gemini and saves it. Identity is taken from the server-side Clerk session, never a request body or email. The database key combines a fingerprint of the Clerk instance's publishable key with the Clerk user ID. Development and production instances therefore have separate profile namespaces. Rotating that instance key or moving users to a production Clerk instance requires an explicit identity migration; copying email addresses is insufficient.

Run `scripts/setup-profiles.ts` with the configured database environment before deploying. It creates the dedicated `gmh_accounts.profiles` table without altering research or application tables. JSONB stores the reviewed structured facts, with optimistic version checks and UTC creation, update and classification timestamps. Saves that conflict with another tab return 409. The database is never exposed to the browser; parameterized queries are scoped to instance and user. Raw uploads remain temporary. Account saves are explicit; the development screen loads an existing account profile after authentication and offers save/reload controls.

Profile endpoints are a reusable production foundation. The `/dev` page and AI workbench endpoints remain unavailable in production. Production launch still requires live Clerk keys, deployment configuration, account-deletion/retention handling, distributed Backboard ownership storage, operational rate limits and product UI. Backboard owns approved practice learning notes; the account profile is structured user data, not a second conversational memory system. Neither profile content nor credentials belong in Git.

## Automatic experience policy v1

Experience is assigned by the LLM during parsing, reclassified on account save and again before personalized question generation. Clients cannot select a target seniority to override it. Users correct facts such as work dates or education completion; the model applies the rubric. This supersedes earlier documentation describing editable experience or target-level overrides.

The rubric distinguishes explicitly completed education, current enrollment/expected completion and unknown status. An expected graduation date passing is not proof that a degree was completed. Future expected graduation is normal. Count evidenced non-overlapping relevant professional work separately from internships and projects. Enrolled students without established professional history receive intern; explicitly graduated/new entrants or people with under two professional years receive entry. Mid requires at least two evidenced professional years and independent delivery scope. Senior requires at least five evidenced years plus cross-team/system ownership or technical leadership. An established professional who is also studying is not forced into intern. Inadequate evidence produces unknown. These are explicit product rules for practice difficulty, not universal occupational standards or hiring eligibility judgments.

The current server date is supplied in UTC, with a human-readable explanation of the applied rule. School prestige, GPA, age, demographic characteristics and assumed graduation completion cannot determine the result. Model classification can still be wrong; evidence and explanations stay visible for fact correction. Timestamps are stored as `timestamptz`; UI presentation must identify UTC or the viewer's local timezone rather than presenting a zone-free date as exact local time.

## Proposed blockchain HR invitations — documentation only

HR will create an interview invitation whose issuance, acceptance, expiry or revocation can be attested through a blockchain. The website remains responsible for delivering a private invitation link and authenticating redemption. The chain is an audit/verification mechanism, not an email delivery system or a substitute for authorization. Choice of chain, transaction sponsorship, wallet abstraction, confirmation policy and cost limits remain undecided; no blockchain code or transactions are implemented.

Keep resumes, candidate names, contact information, answers, reports and bearer invitation secrets off-chain. A proposed transaction records a salted commitment to an opaque invitation identifier and lifecycle state. Redemption verifies the off-chain secret, invitation scope, expiry, use count and revocation status and creates a temporary interviewee profile scoped to that invitation and requisition. A copied transaction or known commitment alone must never grant interview access. Handle pending/failed transactions and reconciliation explicitly rather than showing delivery success before confirmation.

Temporary interviewee profiles must have separate permissions from practice accounts and HR accounts, a defined expiry and deletion schedule, no access to personal practice memory, and only the assigned interview's resources. A candidate may later explicitly link an account through a verified identity flow; do not merge by email alone. Define revocation, repeat invitation handling, dispute retention and off-chain deletion before implementation, since an immutable ledger cannot satisfy deletion of personal data already written to it.
